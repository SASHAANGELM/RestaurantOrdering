# T07 — Idempotent orders and status transitions verification

Verified on 2026-10-18, macOS arm64, with pinned Node **24.22.0** and pnpm **12.14.0** from the existing isolated npm-exec toolchain. Dependencies, shared contracts, schema, and migrations are unchanged.

## Implemented behavior

- `POST /api/orders` accepts only `{ quoteId }` with a UUID `Idempotency-Key` header. Creation returns **201**; a committed same-key/same-payload replay returns **200**, the same order ID and immutable lines, and its current status. A versioned canonical JSON request is hashed with SHA-256. Same-key/different-payload requests return `409 IDEMPOTENCY_CONFLICT` before quote checks. A different key cannot consume the same quote and receives `409 QUOTE_USED` with its existing order ID, even after expiry.
- Confirmation uses one short synchronous `BEGIN IMMEDIATE` transaction. The writer lock is acquired before key/quote/menu reads, so independent writers serialize before making placement decisions. Unique database constraints also protect idempotency keys and quote consumption. An unused quote must be unexpired, have the current persisted menu revision, and still match current item/category eligibility, pricing mode, names/revisions, prices, and calculated totals. Any menu revision change, including an unrelated edit or availability toggled off and back, requires another review with `409 MENU_CHANGED`. No new price is silently accepted.
- Creation inserts a placed order at entity revision one, copies the quote's ordered immutable line snapshots with stable line IDs, and advances the persisted orders stream revision atomically. Separate reviewed quotes can legitimately create separate identical orders. Orders neither reserve nor consume an inventory count.
- `GET /api/orders/by-request/:idempotencyKey` recovers a committed result; an unknown key returns typed `404 NOT_FOUND`. A lookup returning 404 does not rule out a later commit from an in-flight attempt. Keys remain stored with orders. Replay/recovery succeeds after quote expiry, menu edits/archival, status changes, and backend/database reopening.
- `GET /api/orders` returns summaries, matching counts, and a persisted stream revision, newest first by creation timestamp/ID. It supports an optional status filter, defaults to 50 rows, caps pages at 100, and safely returns empty far-out pages. `GET /api/orders/:id` returns immutable lines and totals. Each list/count, detail/lines, or recovery response reads its state and revision inside one read transaction. Key/hash fields are excluded from DTOs. All order endpoints disable caching and use the common correlated validation/error envelope.
- `PATCH /api/orders/:id/status` enforces placed → preparing → ready → completed and cancellation only from placed/preparing. It checks the expected entity revision before transitions or no-ops. A valid change increments entity and stream revisions atomically; stale or invalid requests change nothing. A current-status write at the current revision preserves timestamps/revisions and returns no notification.
- Services return committed `orders.changed` notification data for T08. Replay and no-op results return no notification; failures throw before any result escapes. Socket.IO broadcasting remains T08.

## Demonstrated acceptance and checks

Added **88 feature tests** beside the implementation in `apps/backend/src/modules/orders/orders.spec.ts`, all using isolated temporary real SQLite files:

- Exact HTTP order snapshots, distinct open prices, ordered/stable line IDs, totals, canonical stored hash, initial revisions, detail/recovery DTOs, and unchanged menu availability. Same-key replay creates no extra order/lines/revision/notification. Different payloads conflict, and separate independently reviewed identical quotes can each create orders.
- Eight overlapping HTTP submissions create exactly one order. Separate Node workers, released together against independent SQLite connections, demonstrate same-key replay, same-key/different-payload conflicts, and different-key/same-quote conflicts, with exactly one committed order and stream increment in each race.
- A test destroys the actual confirmation HTTP response at `end()` after the endpoint has committed. The client sees a transport failure, recovers by key, and retries with the original key/payload to obtain the same order without duplication.
- Stop/recreate the HTTP app and reopen/migrate the same temporary database after expiry, Setup edits/archival, and a status update. Replay/recovery returns the original immutable lines and current status. A different key still receives `QUOTE_USED` for the expired consumed quote.
- Expiry at the exact boundary and beyond rejects unused quotes; one millisecond before expiry and zero-total confirmation succeed. Menu availability, item/category archival, fixed-price changes, both pricing-mode switches, unrelated changes, and availability toggled back reject placement. Direct temporary-fixture mutations verify independent eligibility/pricing checks even without a stream increment.
- A failure on the second line insert and a failure on the stream increment both roll back orders, all lines, key/quote consumption, and revisions; the same key/payload can succeed after the injected failure is removed. Invalid persisted snapshot arithmetic is rejected before any order is written. Real writer contention maps to retryable 503, and retry succeeds after release. An attempted concurrent Setup write is blocked across confirmation reads.
- All **25 status pairs** exercise permitted transitions, terminal states, cancellation restrictions, and current-status no-ops. Stale writes (including no-ops), overlapping staff actions, and an injected stream failure preserve correct state. Notifications become visible only after committed state is readable from another connection.
- A 106-order fixture demonstrates bounded pages, newest-first ordering and ID ties, safe far-out pagination, and status-filter count/membership changes. Separate WAL connections commit between reads to verify consistent snapshots for list, detail, and request-key recovery. Malformed bodies/headers/IDs/statuses/pagination and unknown fields receive typed boundary errors.
